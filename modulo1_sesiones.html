Variables de sesión

Cómo PHP recuerda quién inició sesión, por qué cada página privada tiene que comprobarlo en el servidor y cómo se cierra una sesión de verdad.

01 / EN 1 MINUTO

Lo esencial

  1. HTTP no tiene estado: cada pedido llega solo. La sesión hace que el servidor reconozca al mismo usuario entre una página y otra.
  2. Los datos de la sesión ($_SESSION) se guardan en el servidor. El navegador solo guarda el identificador, en la cookie PHPSESSID.
  3. Cada página privada empieza con session_start() y comprueba isset($_SESSION["usuario"]). Si no existe, header("Location: index.php") y exit.
  4. El exit es obligatorio: header() solo manda una cabecera y el script sigue. Sin exit, el HTML privado igual viaja en la respuesta.
  5. Después de un login correcto, session_regenerate_id(true) cambia el identificador y borra el viejo. Protege contra la fijación de sesión.
  6. Un cierre de sesión completo tiene tres pasos: $_SESSION = array(), borrar la cookie con setcookie y una fecha pasada, y session_destroy().
  7. Las cabeceras anti-caché (Cache-Control: no-store…) evitan que el botón “atrás” muestre el panel guardado después de cerrar sesión.
02 / TEORÍA

Conceptos

1. Qué es una sesión

HTTP no recuerda nada: cada página que pedís llega sola al servidor. La sesión sirve para que el servidor sepa que sos el mismo usuario que inició sesión.

ComparaciónEs como la pulsera de un evento. En la entrada te piden el documento (el login) y te ponen una pulsera con un número. Adentro solo miran la pulsera.

2. $_SESSION y la cookie PHPSESSID

$_SESSION es donde PHP guarda los datos del usuario. Esos datos quedan en el servidor. El navegador solo guarda el número de la sesión en una cookie (un dato chico que guarda el navegador) llamada PHPSESSID. La diferencia: la cookie vive en el navegador y solo lleva el identificador; los datos de la sesión viven en el servidor.

// en el servidor:   $_SESSION["usuario"] = "vendedor1";
// en el navegador:  PHPSESSID = 8f3k2a...  (solo el número)

3. Validar la sesión en cada página privada

Cada página privada tiene que preguntar si hay sesión. Si no hay, manda al login. El exit es obligatorio: header() no frena el programa, y sin exit el panel se envía igual.

session_start();
if (!isset($_SESSION["usuario"])) {
    header("Location: index.php");
    exit;
}

4. session_regenerate_id(true) y la fijación de sesión

En la fijación de sesión, el atacante hace que la víctima use un número de sesión que él ya conoce. Cuando la víctima inicia sesión, el atacante entra con ese número. session_regenerate_id(true) cambia el número al iniciar sesión y borra el viejo.

SituaciónEs como cambiarte la pulsera al pasar al sector VIP y romper la vieja. Si alguien copió el número viejo, ya no le sirve.

5. Cerrar sesión bien

Un cierre de sesión completo tiene tres líneas. session_destroy() sola no alcanza: no borra la cookie.

$_SESSION = array();                          // vacía los datos
setcookie(session_name(), "", time() - 42000); // borra la cookie (fecha pasada)
session_destroy();                             // borra la sesión del servidor

6. Cabeceras anti-caché y el botón “atrás”

El navegador guarda copias de las páginas. Después de cerrar sesión, “atrás” puede mostrar la copia del panel. Estas cabeceras (instrucciones que el servidor manda con la página) le dicen que no guarde copias.

header("Cache-Control: no-store, no-cache, must-revalidate");
header("Pragma: no-cache");
header("Expires: 0");
Herramientas del TP. En Firefox, F12 → Almacenamiento → Cookies muestra la cookie PHPSESSID: cambia al iniciar sesión y desaparece al cerrarla. En la terminal, curl -i http://localhost/tp/login_protegido/menu.php pide el panel sin sesión: la vulnerable responde 200 con el panel, y la protegida, 302 (redirección) al login. -i muestra las cabeceras de la respuesta (por ejemplo el 302 y el Location) y curl no sigue la redirección salvo que se use -L.

05 / CÓDIGO

El código explicado

Código real del proyecto del grupo (carpetas login_vulnerable y login_protegido). Se muestran solo las partes de la sesión; la conexión a la base no se incluye.

1. El panel: menu.php

Vulnerable

//Cualquiera que escriba la URL menu.php ve el panel.
session_start();
$usuario=$_SESSION["usuario"] ?? "desconocido";
$tipo=$_SESSION["tipo"] ?? "desconocido";
?>
...
<p class="dato"><span class="clave">usuario:</span> <span class="valor"><?php echo $usuario; ?></span></p>

Abre la sesión y lee los datos, pero no comprueba nada: cualquiera que escriba la URL ve el panel, con usuario “desconocido”.

Protegido 
session_start();
//PROTECCION: se valida la sesion en el servidor antes de mostrar cualquier HTML
if(!isset($_SESSION["usuario"])){
    header("Location: index.php");
    exit;
}
//PROTECCION: cabeceras no-cache para que el boton "atras" no muestre el panel despues del logout
header("Cache-Control: no-store, no-cache, must-revalidate");
header("Pragma: no-cache");
header("Expires: 0");
$usuario=$_SESSION["usuario"] ?? "desconocido";
$tipo=$_SESSION["tipo"] ?? "desconocido";

Sin sesión, redirige al login y no envía el panel.

2. El login correcto: php/acceso.php

Vulnerable 
}else if($clave==$fila["usu_clave"]){
    //guardamos los datos del usuario en la sesion (sin session_regenerate_id)
    $_SESSION["usuario"]=$fila["usu_nombre"];
    $_SESSION["tipo"]=$fila["usu_tipo"];
    echo"OK";//OK con mayusculas
}else{
    echo "CONTRASEÑA INCORRECTA";
}

Guarda los datos en la sesión, pero con el mismo ID que tenía antes del login: queda expuesto a fijación de sesión.

Protegido 
}else if($clave==$fila["usu_clave"]){
    //PROTECCION: nuevo ID de sesion al autenticar (true borra la sesion vieja del servidor)
    session_regenerate_id(true);
    //guardamos los datos del usuario en la sesion
    $_SESSION["usuario"]=$fila["usu_nombre"];
    $_SESSION["tipo"]=$fila["usu_tipo"];
    echo"OK";//OK con mayusculas
}else{
    echo "CONTRASEÑA INCORRECTA";
}

Nuevo identificador y datos del usuario guardados en el servidor.

3. El cierre de sesión: php/logout.php

Vulnerable 
//VULNERABLE: el "cierre de sesion" solo redirige al login.
//No se vacia $_SESSION, no se borra la cookie y no se destruye la sesion en el servidor.
header("Location: ../index.php");
exit;

La sesión sigue viva en el servidor y la cookie sigue en el navegador.

Protegido 
session_start();
//PROTECCION: se vacian todas las variables de sesion
$_SESSION=array();
//PROTECCION: se borra la cookie de sesion del navegador
$parametros=session_get_cookie_params();
setcookie(session_name(), "", time()-42000,
    $parametros["path"], $parametros["domain"],
    $parametros["secure"], $parametros["httponly"]
);
//PROTECCION: se destruye la sesion en el servidor
session_destroy();
header("Location: ../index.php");
exit;

Es el mismo esquema que recomienda el manual de PHP en session_destroy.

06 / ESCENARIOS

Ejemplos paso a paso

1. Acceso directo por URL sin iniciar sesión

Acción: alguien que conoce el nombre del archivo escribe localhost/tp/.../menu.php sin pasar por el login.

Vulnerable

Se muestra el panel, con usuario “desconocido”. Es la prueba principal que el grupo comprobó.

Protegido

isset no encuentra $_SESSION["usuario"], redirige a index.php y exit corta el script.

2. Cerrar sesión y tocar “atrás”

Acción: el usuario entra al panel, cierra sesión y aprieta el botón “atrás” del navegador (después, “adelante”).

Vulnerable

Vuelve al panel: el logout solo redirigió, la sesión sigue viva y, además, menu.php no valida nada.

Protegido

La sesión fue destruida y la página no quedó en caché: el navegador la vuelve a pedir, la validación falla y vuelve al login.

3. Equipo compartido: otra persona usa el navegador después del logout

Acción: el vendedor cierra sesión y se va. Un compañero abre el historial y entra a menu.php.

Vulnerable

Entra al panel con los datos internos.

Protegido

La cookie se borró y la sesión del servidor ya no existe: redirige al login.

4. Fijación de sesión

Acción: el atacante entra al login, anota su PHPSESSID y logra que la víctima use ese mismo identificador; la víctima inicia sesión.

Sin regenerar el ID

Después del login el ID sigue igual. El atacante pone ese ID en su navegador y entra como la víctima.

Protegido

session_regenerate_id(true) da un ID nuevo a la víctima y borra el viejo. El ID del atacante no sirve.

5. Se olvidaron el exit

Acción: en menu.php está el header("Location: ...") pero falta el exit. Alguien ejecuta curl -i .../menu.php.

Sin exit

La respuesta tiene 302 y Location, pero en el cuerpo viene el HTML del panel. En el navegador “parece” protegido porque redirige rápido.

Con exit

302 con el cuerpo vacío. No sale nada del panel.

6. Login legítimo

Acción: un empleado ingresa usuario y contraseña correctos.

Vulnerable

Entra al panel; se guardan nombre y tipo en $_SESSION, pero sin regenerar el ID.

Protegido

Se verifica en la base, se regenera el ID, se guardan nombre y tipo en $_SESSION y entra. La protección no impide el uso correcto.

Trampas de examen

“header("Location: ...") corta la ejecución.”No. Solo agrega una cabecera; sin exit el script sigue y manda el HTML.

09 / REPASO

Preguntas probables

Tocá cada pregunta para ver la respuesta.

¿Por qué HTTP necesita sesiones?

Porque no tiene estado: cada pedido es independiente y el servidor no recuerda quién inició sesión. La sesión guarda los datos en el servidor y le da al navegador un identificador.

¿Qué guarda la cookie PHPSESSID?

Solo el identificador de la sesión. Los datos ($_SESSION) quedan en el servidor.

¿Qué hace session_start()?

Crea una sesión nueva o reanuda la existente según el identificador que manda el navegador. Va antes de cualquier HTML.

¿Cómo se valida una página privada?

session_start(); si !isset($_SESSION["usuario"]), header("Location: index.php") y exit.

¿Por qué hace falta el exit después del header?

Porque header() no detiene el script. Sin exit, el HTML privado se manda igual en la respuesta.

¿Qué es la fijación de sesión y cómo se evita?

El atacante hace que la víctima inicie sesión con un ID que él conoce. Se evita con session_regenerate_id(true) después de autenticar.

¿Qué significa el true de session_regenerate_id(true)?

Que además de crear el ID nuevo, borra la sesión vieja del servidor.

¿Cuáles son los pasos de un cierre de sesión completo?

session_start(), $_SESSION = array(), setcookie con fecha pasada y session_destroy(); después redirigir y exit.

¿Para qué sirven las cabeceras anti-caché?

Para que el navegador no guarde el panel y “atrás” no lo muestre después del logout.

¿Qué se demostró con la prueba principal?

Que en la vulnerable se entra a menu.php escribiendo la URL y en la protegida redirige al login.

¿Para qué usaron curl y las herramientas de Firefox?

curl, para pedir páginas sin sesión y ver la respuesta real del servidor (200 o 302). Firefox, para ver la cookie PHPSESSID, si cambia al iniciar sesión y si se borra al cerrar.

10 / TÉRMINOS

Glosario

HTTP sin estado
Cada pedido es independiente; el servidor no recuerda los anteriores.
Sesión
Datos de un usuario guardados en el servidor mientras navega, asociados a un identificador.
Identificador de sesión (ID)
Cadena aleatoria que relaciona al navegador con su sesión en el servidor.
PHPSESSID
Nombre por defecto de la cookie donde PHP guarda el identificador.
Cookie
Dato pequeño que el servidor pide guardar al navegador, que lo reenvía en cada pedido.
$_SESSION
Arreglo superglobal de PHP con las variables de sesión.
session_start()
Crea o reanuda la sesión.
session_regenerate_id(true)
Cambia el identificador y borra la sesión vieja.
session_destroy()
Elimina los datos de la sesión en el servidor.
session_get_cookie_params()
Devuelve los parámetros de la cookie de sesión (ruta, dominio, secure, httponly).
setcookie()
Envía una cookie; con fecha pasada, la borra.
header("Location: ...")
Cabecera de redirección (302). No detiene el script.
exit
Termina la ejecución del script.
Fijación de sesión
El atacante hace usar a la víctima un ID que él conoce y lo aprovecha después del login (CWE-384).
Secuestro de sesión
El atacante roba un ID ya autenticado y lo usa.

Entrar a una página privada escribiendo su dirección.
Cache-Control: no-store

Marcas de la cookie: no la lee JavaScript / solo por HTTPS / limita su envío desde otros sitios.
curl
Programa de terminal para hacer pedidos HTTP; -i muestra cabeceras, -b envía cookies.
