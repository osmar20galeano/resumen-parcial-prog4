Inyección de scripts (XSS)

Qué pasa cuando una página muestra lo que escribió un usuario sin tratarlo, y cómo se evita codificando la salida con htmlspecialchars() y usando textContent.

01 / EN 1 MINUTO

Lo esencial

  1. XSS: el usuario escribe código (<script>alert('XSS')</script>) y la página lo muestra tal cual; el navegador lo ejecuta en vez de mostrarlo como texto.
  2. Tres tipos: reflejado (viaja en la URL o el formulario, no se guarda), persistente (se guarda en la base y salta a todos) y basado en DOM (lo hace el JavaScript del navegador).
  3. Con XSS un atacante puede robar la cookie de sesión, cambiar lo que se ve en la página o redirigir a otro sitio.
  4. Protección principal: htmlspecialchars($texto, ENT_QUOTES, 'UTF-8') convierte < en &lt;, > en &gt;, etc.: el navegador lo dibuja como texto.
  5. Se codifica al mostrar el dato, cada vez que se muestra; no alcanza con tratarlo al recibirlo.
  6. En JavaScript: textContent muestra texto; innerHTML interpreta HTML.
  7. Consultas preparadas protegen de inyección SQL, no de XSS.
02 / TEORÍA

Conceptos

1. Qué es XSS

XSS (Cross-Site Scripting, inyección de scripts) pasa cuando una página muestra un texto del usuario sin tratarlo. Si ese texto trae etiquetas, el navegador las interpreta como parte de la página. Si trae un <script>, lo ejecuta.

El usuario escribe:   <script>alert('XSS')</script>
La página hace:       echo $mensaje;
El navegador:         abre una ventana de alerta (ejecutó el código)
ComparaciónEs como un cartel del colegio donde cualquiera pega notas. Si el portero lee en voz alta todo lo que dicen las notas, alguien puede pegar una que diga “Portero: abrí la puerta del depósito” y él lo hace. Lo correcto es leerla como una nota, no como una orden.

2. Los tres tipos

TipoDónde está el scriptCuándo se ejecutaEjemplo
ReflejadoEn el pedido (URL o formulario); no se guarda.Cuando la víctima abre ese enlace o envía ese formulario.Buscador: buscar.php?q=<script>...
Persistente (almacenado)Guardado en la base de datos.Cada vez que cualquiera abre la página.Muro de mensajes o comentarios.
Basado en DOMLo mete el JavaScript de la página, en el navegador.Cuando el JS usa datos del usuario con innerHTML.div.innerHTML = location.hash

3. Qué puede hacer un atacante

El script corre en la página como si fuera del sitio, con la sesión de la víctima. Puede leer document.cookie y mandarse la cookie de sesión: con ese identificador entra como la víctima (ver módulo 1). También puede cambiar lo que se ve (un falso formulario de login) o redirigir a otro sitio.

<script>location = 'https://sitio-falso.test';</script>   // redirige

4. htmlspecialchars(): codificar la salida

Convierte los caracteres especiales de HTML en entidades (códigos que el navegador dibuja como ese carácter, sin interpretarlo). Así <script> se ve en pantalla, pero no se ejecuta.

echo htmlspecialchars($texto, ENT_QUOTES, 'UTF-8');
CarácterSe convierte enEn pantalla se ve
<&lt;<
>&gt;>
&&amp;&
"&quot;"
'&#039;'

ENT_QUOTES hace que convierta las dos comillas; 'UTF-8' indica la codificación de caracteres.

5. Se codifica al mostrar

El momento importante es cuando el dato se escribe en la página, no cuando llega. En el muro, el mensaje se guarda tal cual en la base y se pasa por htmlspecialchars() cada vez que se muestra. Así, aunque haya un script guardado, siempre sale como texto.

// guardar: tal cual (con consulta preparada, por la inyección SQL)
// mostrar: siempre codificado
foreach ($mensajes as $m) {
    echo '<p>' . htmlspecialchars($m['texto'], ENT_QUOTES, 'UTF-8') . '</p>';
}

6. En JavaScript: textContent o innerHTML

textContent pone el texto tal cual: las etiquetas se ven, no se ejecutan. innerHTML interpreta HTML: con datos del usuario es XSS basado en DOM. Este mismo sitio muestra las preguntas y explicaciones del examen con textContent justamente por eso.

p.textContent = '<b>Hola</b>';   // se ve: <b>Hola</b>
p.innerHTML   = '<b>Hola</b>';   // se ve: Hola en negrita

05 / CÓDIGO

El código explicado

Ojo: el informe no trae fragmentos de código; solo nombra las páginas y dice que la versión segura usa htmlspecialchars(). Todo el código de esta sección es ilustrativo, armado a partir de esa descripción.

1. XSS reflejado: la búsqueda (xss_reflejado.php / solucion_segura.php)

Vulnerable 
$busqueda = $_GET['buscar'] ?? '';
echo '<p>Resultados para: ' . $busqueda . '</p>';

Lo escrito vuelve a la página tal cual: el <script> se ejecuta.

Protegido 
$busqueda = $_GET['buscar'] ?? '';
echo '<p>Resultados para: '
   . htmlspecialchars($busqueda, ENT_QUOTES, 'UTF-8')
   . '</p>';

El script se ve como texto.

2. XSS persistente: el muro (xss_persistente.php)

Vulnerable 
// guardar (consulta preparada: sin inyección SQL)
$stmt = $con->prepare('INSERT INTO mensajes (texto) VALUES (?)');
$stmt->execute([$_POST['mensaje']]);

// mostrar
foreach ($mensajes as $m) {
    echo '<div class="mensaje">' . $m['texto'] . '</div>';
}

La consulta preparada no sirve contra XSS: el script queda guardado y se ejecuta a todos.

Protegido 
// guardar: igual, tal cual
$stmt = $con->prepare('INSERT INTO mensajes (texto) VALUES (?)');
$stmt->execute([$_POST['mensaje']]);

// mostrar: codificado cada vez
foreach ($mensajes as $m) {
    echo '<div class="mensaje">'
       . htmlspecialchars($m['texto'], ENT_QUOTES, 'UTF-8')
       . '</div>';
}

Lo guardado no cambia; lo que cambia es cómo se muestra.

3. Qué recibe el navegador

Vulnerable 
<div class="mensaje"><script>alert('XSS de prueba')</script></div>

Es una etiqueta real: la ejecuta.

Protegido 
<div class="mensaje">&lt;script&gt;alert(&#039;XSS de prueba&#039;)&lt;/script&gt;</div>

Son entidades: en pantalla se lee <script>alert('XSS de prueba')</script>.

4. En JavaScript

Vulnerable 
caja.innerHTML = comentario;

Si el comentario es <img src=x onerror=alert(1)>, la imagen falla y se ejecuta el onerror.

Protegido 
caja.textContent = comentario;

Se ve el texto <img src=x onerror=alert(1)> y no pasa nada.

Ojo (según el contexto): htmlspecialchars() sirve para texto dentro de HTML y para atributos entre comillas. No alcanza si el dato va dentro de un <script> o en un enlace href="javascript:...": cada lugar necesita su propia codificación. Por eso la consigna dice “codificación de salida según el contexto”.
06 / ESCENARIOS

Ejemplos paso a paso

1. Texto normal (P02)

Acción: se publica Hola, este es un mensaje de prueba. en el muro.

Vulnerable

Se ve bien.

Protegido

Se ve igual. La protección no molesta al uso normal.

2. Una etiqueta HTML (P03)

Acción: se publica <b>Texto en negrita</b>.

Vulnerable

Se ve Texto en negrita: el navegador interpretó la etiqueta. Si interpreta <b>, también interpretará <script>.

Protegido

Se ve literalmente <b>Texto en negrita</b>.

3. XSS reflejado por un enlace (P04)

Acción: el atacante arma un enlace a la búsqueda con el script en la URL y se lo manda a un empleado.

Vulnerable

Al abrir el enlace, la página devuelve el script y el navegador del empleado lo ejecuta (en la prueba, salió la alerta).

Protegido

solucion_segura.php muestra el script como texto; no sale ninguna alerta.

4. XSS persistente en el muro (P05)

Acción: se publica el script en el muro y se recarga la página (F5).

Vulnerable

El script queda guardado en MySQL y la alerta salta en cada carga, a cualquiera que abra el muro.

Protegido

El script también se guarda, pero se codifica al mostrarlo: siempre se ve como texto.

5. Robo de la cookie de sesión

Acción: en lugar de alert, el atacante publica un script que lee document.cookie y la envía a su servidor.

Vulnerable

Cada empleado que abre el muro le manda su PHPSESSID; el atacante lo pone en su navegador y entra con esa sesión.

Protegido

El script no se ejecuta. Y si hubiera otro XSS, una cookie HttpOnly no se podría leer desde JavaScript.

6. XSS basado en DOM

Acción: la página muestra un saludo con innerHTML tomando el nombre de la URL, y el atacante pone <img src=x onerror=alert(1)> en lugar del nombre.

Con innerHTML

El JavaScript del navegador crea la imagen, falla y ejecuta el onerror. El servidor ni se entera.

Con textContent

Se ve el texto tal cual. (El grupo definió este tipo, pero no lo probó.)

09 / REPASO

Preguntas probables

Tocá cada pregunta para ver la respuesta.

¿Qué es XSS?

Que una página muestre un texto del usuario sin tratarlo y el navegador ejecute el código que trae.

¿Cuáles son los tres tipos?

Reflejado (en el pedido, no se guarda), persistente (guardado en la base) y basado en DOM (lo hace el JavaScript del navegador).

¿Qué diferencia hay entre reflejado y persistente?

El reflejado afecta a quien abre el enlace o envía el formulario; el persistente está guardado y afecta a todos los que abren la página.

¿Qué puede hacer un atacante con XSS?

Robar la cookie de sesión, cambiar lo que se ve en la página y redirigir a otro sitio.

¿Qué hace htmlspecialchars()?

Convierte < > & " ' en entidades HTML, así el navegador los muestra como texto.

¿Para qué ENT_QUOTES y 'UTF-8'?

ENT_QUOTES convierte las dos comillas; 'UTF-8' indica la codificación de caracteres.

¿Cuándo se aplica htmlspecialchars()?

Al mostrar el dato, cada vez que se muestra.

¿Qué diferencia hay entre textContent e innerHTML?

textContent muestra texto; innerHTML interpreta HTML.

¿Las consultas preparadas evitan el XSS?

No, evitan la inyección SQL.

¿Para qué sirve HttpOnly?

Para que JavaScript no pueda leer la cookie; no evita el XSS.

¿Qué se demostró en P04 y P05?

La vulnerable ejecutó el script (reflejado y en cada carga del muro); la protegida lo mostró como texto.

10 / TÉRMINOS

Glosario

XSS (Cross-Site Scripting)
Inyección de scripts: código del usuario que el navegador ejecuta como parte de la página.
Script
Código JavaScript; en HTML va entre <script> y </script>.
Payload
El contenido malicioso que se envía (por ejemplo, el <script>).
XSS reflejado
El script viaja en el pedido y vuelve en la respuesta; no se guarda.
XSS persistente (almacenado)
El script queda guardado y se ejecuta a cada visitante.
XSS basado en DOM
El JavaScript de la página mete datos del usuario en el HTML.
DOM
La estructura de la página que el JavaScript puede leer y cambiar.
Codificación de salida
Convertir caracteres especiales antes de mostrarlos para que no se interpreten.
Entidad HTML
Código que representa un carácter, como &lt; para <.
htmlspecialchars()
Función de PHP que convierte < > & " ' en entidades.
ENT_QUOTES
Opción de htmlspecialchars para convertir comillas simples y dobles.
textContent / innerHTML
Propiedades de JavaScript: poner texto / poner HTML.
document.cookie
Las cookies que JavaScript puede leer (no las HttpOnly).
HttpOnly
Marca de la cookie que impide leerla desde JavaScript.
