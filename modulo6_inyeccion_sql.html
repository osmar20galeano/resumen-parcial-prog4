Inyección SQL

Qué pasa cuando lo que escribe el usuario se pega dentro de la consulta SQL, cómo se rompe un login así y por qué las consultas preparadas lo evitan.

01 / EN 1 MINUTO

Lo esencial

  1. Inyección SQL: el dato que escribe el usuario termina siendo parte del código SQL y cambia lo que hace la consulta.
  2. Pasa cuando la consulta se arma concatenando: "... WHERE usuario = '$usuario'".
  3. La comilla ' cierra el texto, OR '1'='1 hace verdadera la condición y -- o # comentan el resto.
  4. La defensa es la consulta preparada: primero va la estructura con ? y después los datos, que nunca se interpretan como código.
  5. En mysqli: prepare() → bind_param() → execute() → get_result().
  6. En la prueba del grupo, ana' -- - entró sin la clave en la versión vulnerable y la protegida respondió 401.
  7. El hash de contraseñas no evita la inyección SQL, y la consulta preparada no evita el XSS.
02 / TEORÍA

Conceptos

1. Qué es la inyección SQL

Una consulta SQL es una orden para la base de datos. Si el programa pega adentro lo que escribió el usuario, ese texto puede traer pedazos de SQL que cambian la orden. Entonces la base hace lo que dice el atacante, no lo que quería el programador.

ComparaciónEs como un formulario de banco que dice “Pagar a: ______”. Si alguien escribe “Juan. Además, vaciar la cuenta” y el cajero lee todo como una orden, hace las dos cosas. Lo correcto es leer lo del hueco solo como un nombre.

2. Concatenar contra consulta preparada

Vulnerable 
$sql = "SELECT * FROM usuarios
        WHERE usuario = '$usuario' AND clave = '$clave'";

Los datos se pegan dentro del texto de la consulta.

Protegido 
$sql = "SELECT * FROM usuarios
        WHERE usuario = ? AND clave = ?";

Los ? son huecos; los datos van aparte.

3. Cómo se rompe un login concatenado

Tres piezas: la comilla ' cierra el texto antes de tiempo; OR '1'='1' agrega una condición que siempre es verdadera; y -- (con un espacio después) o # convierten en comentario todo lo que sigue. Ejemplo clásico de laboratorio, en usuario y clave:

Usuario:  ' OR '1'='1
Clave:    ' OR '1'='1

Consulta que queda armada:
SELECT * FROM usuarios WHERE usuario = '' OR '1'='1' AND clave = '' OR '1'='1'
-- el último OR '1'='1' es siempre verdadero: la condición entera da verdadero

La condición termina siendo verdadera para todas las filas: la consulta devuelve usuarios y el login deja entrar. Solo para probar en un entorno local propio.

4. Por qué la consulta preparada lo evita

Con prepare() se manda primero la estructura de la consulta, con los ?. La base la analiza y la deja fija. Después, con bind_param(), se mandan los datos: la base los usa solo como valores, nunca como código. Si alguien escribe ' OR '1'='1, se busca un usuario que se llame literalmente así.

5. prepare, bind_param, execute y get_result

bind_param() lleva una letra por cada ?, en el mismo orden: s = texto (string), i = entero, d = decimal (double).

$stmt = $con->prepare("SELECT id, nombre FROM usuarios WHERE usuario = ?");
$stmt->bind_param("s", $usuario);       // 1 ? → 1 letra
$stmt->execute();
$resultado = $stmt->get_result();       // el resultado del SELECT
$fila = $resultado->fetch_assoc();      // una fila como arreglo

$stmt = $con->prepare("INSERT INTO productos (nombre, stock, precio) VALUES (?, ?, ?)");
$stmt->bind_param("sid", $nombre, $stock, $precio);   // 3 ? → 3 letras
$stmt->execute();

6. El apóstrofo en un nombre

No hace falta un atacante para romper una consulta concatenada: un cliente que se llama O'Brien tiene una comilla en el nombre. Esa comilla cierra el texto antes de tiempo y la consulta da error. Con la consulta preparada, el nombre se guarda tal cual.

INSERT INTO clientes (nombre) VALUES ('O'Brien')   -- error de sintaxis: el texto termina en 'O'
INSERT INTO clientes (nombre) VALUES (?)           -- con bind_param("s", $nombre): se guarda O'Brien

05 / CÓDIGO

El código explicado

1. Las consultas que registró el sistema (reales, Anexo B)

Vulnerable 
SELECT id, nombre FROM acceso_lectura WHERE usuario = 'ana' -- -' AND 0 = 1 LIMIT 1

Se aceptó el acceso.

Protegido 
SELECT id, nombre FROM acceso_lectura WHERE usuario = ? AND ? = 1 LIMIT 1

Se rechazó la entrada manipulada.

Cómo leer la vulnerable. El sistema arma la condición con el usuario y con el resultado de verificar la clave (0 = clave incorrecta). En el campo usuario se escribió ana' -- -:

  • ana es un usuario que existe.
  • ' cierra el texto del usuario.
  • -- - abre un comentario: todo lo que sigue (' AND 0 = 1 LIMIT 1) se ignora. El - final asegura que haya un espacio después de --, que MySQL necesita para tomarlo como comentario.

La base ejecuta en realidad SELECT id, nombre FROM acceso_lectura WHERE usuario = 'ana': desapareció el control de la clave. En la protegida, los dos ? reciben los datos aparte: se busca un usuario llamado literalmente ana' -- - con clave correcta 0 = 1, y no hay ninguno.

2. El login en PHP

Ojo: el informe no trae el código PHP, solo las consultas registradas. El código de esta parte es ilustrativo, con mysqli como en clase. Compara la clave en la consulta para que se vea simple; en un sistema real la clave se guarda con hash y se verifica con password_verify() (módulo 2).
Vulnerable 
$usuario = $_POST['usuario'];
$clave   = $_POST['clave'];

$sql = "SELECT id, nombre FROM usuarios
        WHERE usuario = '$usuario' AND clave = '$clave'";
$resultado = $con->query($sql);
$fila = $resultado->fetch_assoc();

if ($fila) {
    $_SESSION['usuario'] = $fila['nombre'];
}

Lo que escribe el usuario pasa a ser parte del SQL.

Protegido 
$usuario = $_POST['usuario'];
$clave   = $_POST['clave'];

$sql = "SELECT id, nombre FROM usuarios
        WHERE usuario = ? AND clave = ?";
$stmt = $con->prepare($sql);
$stmt->bind_param("ss", $usuario, $clave);
$stmt->execute();
$resultado = $stmt->get_result();
$fila = $resultado->fetch_assoc();

if ($fila) {
    $_SESSION['usuario'] = $fila['nombre'];
}

La estructura queda fija; los datos van aparte.

06 / ESCENARIOS

Ejemplos paso a paso

1. La entrada del informe: ana' -- - (S02 y S03)

Acción: se escribe ana' -- - como usuario y una clave incorrecta.

Vulnerable

Queda WHERE usuario = 'ana' -- -' AND 0 = 1. Lo que sigue a -- es comentario: se entra al menú con la clave incorrecta.

Protegido

Se busca un usuario llamado ana' -- -: no existe. HTTP 401 y vuelta al login.

2. El clásico: ' OR '1'='1

Acción: se escribe ' OR '1'='1 en usuario y en clave.

Vulnerable

WHERE usuario = '' OR '1'='1' AND clave = '' OR '1'='1': siempre verdadero, devuelve filas y deja entrar.

Protegido

Se busca un usuario cuyo nombre es el texto ' OR '1'='1: no hay. Rechazado.

3. Con # en lugar de --

Acción: se escribe ana'# como usuario.

Vulnerable

WHERE usuario = 'ana'#' AND clave = '...': en MySQL, # también es comentario. Entra como ana.

Protegido

El # es parte del texto del usuario. Rechazado.

4. Credenciales normales, pero incorrectas (S01)

Acción: un usuario real con una clave equivocada, sin nada raro.

Vulnerable

HTTP 401: sin inyección, la consulta funciona como se esperaba.

Protegido

HTTP 401.

5. Un cliente que se llama O'Brien (C02)

Acción: se da de alta un cliente con un apóstrofo en el nombre.

Concatenada

La comilla cierra el texto: error de sintaxis y el cliente no se guarda. (Es lo que pasaría; el grupo lo probó solo con la preparada.)

Preparada

Se guarda tal cual y el JOIN con la ciudad funciona: “el apóstrofo no altera el SQL”.

6. Mostrar el error de MySQL

Acción: el atacante escribe una comilla sola para ver qué pasa.

Con die($con->error)

Aparece el error de MySQL con parte de la consulta: el atacante aprende nombres de tablas y columnas.

Mensaje genérico

“No se pudo iniciar sesión”. El error real queda en un registro del servidor.

Trampas de examen

“Uso consultas preparadas, así que no tengo XSS.”Protegen la base, no lo que se muestra en la página (módulo 5).

09 / REPASO

Preguntas probables

Tocá cada pregunta para ver la respuesta.

¿Qué es la inyección SQL?

Que el dato que escribe el usuario termine siendo parte del código SQL y cambie la consulta.

¿Por qué es peligroso concatenar?

Porque el texto del usuario se mezcla con la estructura de la consulta.

¿Qué hacen la comilla, el OR y el comentario?

La comilla cierra el texto; OR '1'='1 hace la condición siempre verdadera; -- o # anulan el resto de la consulta.

¿Cómo evita la inyección la consulta preparada?

Manda primero la estructura con ? y después los datos, que se usan solo como valores.

¿Qué hacen prepare, bind_param, execute y get_result?

Preparar la estructura, asociar los datos con su tipo, ejecutar y traer el resultado.

¿Qué significan s, i y d en bind_param?

Texto, entero y decimal. Va una letra por cada ?.

¿Qué pasó con ana' -- - en el informe?

En la vulnerable entró con la clave incorrecta (el comentario anuló AND 0 = 1). En la protegida, 401.

¿Qué pasa con O'Brien?

Rompe la consulta concatenada; con la preparada se guarda bien (C02).

¿El hash de contraseñas evita la inyección SQL?

No; protege las claves guardadas, otro problema.

¿Se puede usar ? para el nombre de una tabla?

No, solo para valores. Para tablas o columnas se usa una lista de nombres permitidos.

¿Por qué no mostrar el error de MySQL?

Porque da pistas de la estructura de la base.

¿Qué significan 401, 302, 409 y 422?

No autorizado, redirección, conflicto y datos que no se pueden procesar.

10 / TÉRMINOS

Glosario

SQL
Lenguaje para pedirle cosas a la base de datos.
Inyección SQL
Que un dato del usuario se convierta en parte del código SQL.
Concatenar
Pegar textos; aquí, pegar el dato dentro de la consulta.
Consulta preparada (parametrizada)
Consulta con ? en lugar de los datos, que se mandan aparte.
prepare()
Prepara la estructura de la consulta.
bind_param()
Asocia los datos a los ?, con su tipo (s, i, d).
execute()
Ejecuta la consulta preparada.
get_result() / fetch_assoc()
Traer el resultado / leer una fila como arreglo.
Comentario SQL
-- (con espacio) o #: lo que sigue se ignora.
Payload
La entrada preparada para el ataque (ej.: ' OR '1'='1).
Escapar
Marcar caracteres especiales para que no se interpreten; no es la defensa principal.
Privilegios mínimos
Que el usuario de la base solo pueda hacer lo necesario.
Clave foránea (FK)
Columna que relaciona un registro con otro (ej.: cliente con ciudad).
409 / 422
Conflicto / datos que no se pueden procesar.
